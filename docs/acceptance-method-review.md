# 验收手法自检（2026-10-24）

用一批**受控实验**检验"我用来验收的手段"本身是否可靠。结论：**不可靠的地方比预想多**，
但修好之后能给出可信结论。

## 一、四个实测到的手法问题

| # | 问题 | 实验 | 结果 |
|---|---|---|---|
| 1 | `clicked: true` **假阳性** | 点窗口外的 (40,40) | 仍返回 `"clicked": true` —— 它只表示"事件注入成功"，与是否命中无关 |
| 2 | `--expect changed` **假阴性** | 点侧栏 Disk（页面确实切到 Disk） | `status: expectation_failed / changed=False`，但随后 tree 读到页头已经是 `Disk` |
| 3 | 文本匹配有**歧义** | `press --text "Clean"` | 同时匹配应用名、窗口名、侧栏按钮；工具拒绝猜（正确），但换个宽松实现就会点错 |
| 4 | **焦点丢失** | 连续动作之间 | 窗口被压到后台，点击落到别的 App（整屏截图可见 CodeBuddy 在前面） |

第 1、2 条是致命的：**工具说"成功"不等于生效，工具说"失败"也不等于没生效**。

## 二、三条站得住的取证手段

| 手段 | 为什么可靠 | 本次用法 |
|---|---|---|
| **动作后独立读状态** | 读的是 UI 的真实文本，不依赖工具的判断 | 五页切换逐个读页头：`Disk → System → AI Access → Clean → Apps` 全部命中 |
| **磁盘事实** | 绕过 UI，直接看文件系统 | 清理后 `~/Library/Caches` 为空、`.Trash` 多出 3 个文件、回执 JSON 落盘 |
| **截图** | 人眼可复核，作为交叉证据 | 语言切换、页面内容 |

## 三、修正后的 SOP

```
1. focus（每次动作前）
2. 用 --path 精确定位（--text 只在确认唯一时用）
3. 动作（press 优先于坐标 click）
4. **独立取证**：tree 读期望文本 / ls 看磁盘 / 截图
5. 断言写进脚本（不是看工具返回的 success）
```

**明令禁止**：
- 以 `clicked/pressed: true` 作为"操作生效"的证据；
- 以 `--expect changed` 作为唯一判据（会假阴性）。

## 四、对之前结论的影响（诚实评级）

| 结论 | 依据 | 置信度 |
|---|---|---|
| 五页导航正常 | tree 读页头（本次独立复核） | **高** |
| 清理全流程：14.8 MB → 废纸篓、回执生成、释放 0 B | 磁盘事实 | **高** |
| 卸载面板：`含应用本体 + 残留 1 项`、取消后无删除 | tree 文本 + 文件仍在 | **高** |
| 更新页：formula 74 / cask 2 / App Store 1 / npm 2 / Electron 4 / 无法检测 24 | tree 文本 | **高** |
| 磁盘、系统、AI 三页数据 | tree 文本 | **高** |
| **语言菜单"点击"可用** | 只测过 `defaults` 切换，点击路径未取证 | **低** |
| "点击没反应 = 控件 bug" | 坐标点击 + 焦点丢失导致 | **已推翻**（用户实测正常；我误判） |

## 五、教训

1. **工具的 success 字段不是证据**，动作后的**状态**才是；
2. **断言工具本身要先校准**：用两个已知结果（一定变 / 一定不变）喂给它。
   这次 `--expect` 假阴性就是没做校准；
3. 只在自动化里出现的怪现象，**先怀疑测试手法**，别改产品代码（今天为这个白改了一版控件，后已回退）；
4. 破坏性动作（卸载/清理）一律在**沙盒家目录**里做，只读动作才碰真实数据。

## 六、工具够不到的控件（这轮实证）

有些 SwiftUI 控件，GUI 自动化**根本无法验证**，只能人来点：

| 现象 | 实证 |
|---|---|
| AX 树里完全没有该控件 | 语言栏（侧栏 `safeAreaInset` 底部）在 227 个节点里查不到；`element-at` 命中的是覆盖它的 `AXScrollArea` |
| 坐标事件也驱动不了 | CGEvent 的 `click` 与带轨迹的 `mouseMoved` 都到不了 `onTapGesture` / `onHover`，`clicked: true` 依旧返回 true |
| 加无障碍属性后更糟 | 用 `Button` 包裹 + `accessibilityAddTraits(.isButton)` 后控件从树里彻底消失 |

结论：**这类控件的验收只能由人完成**。自动化能做的是把"落点/状态/外观"证据准备好，
把"交互是否生效"明确标注为未验证，而不是编一个通过。
